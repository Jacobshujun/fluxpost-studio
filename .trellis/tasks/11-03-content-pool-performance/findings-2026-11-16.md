# Batch content-pool configuration latency investigation — November 16

## Scope and method

Investigated `小红书图文重构-jacob 批量任务 副本 20261116-121109` in response to the user's renewed latency report. The persisted content-pool parameter selects 95 IDs manually and samples two randomly. The owning account has effective administrator access. The running `/api/version` reports `c77d2952d67554f2b46b78e15cd395a0fd014e4f`, which includes the November 13 implementation.

All runtime database access used PostgreSQL connections with `default_transaction_read_only=on` and a 20-second statement timeout. No schedule preview/launch API, providers, Feishu, account mutation, or runtime restart was invoked. Read-only profiling called the current domain implementation from an ignored esbuild diagnostic bundle. Its only instrumentation changes skip database initialization/migrations, enforce read-only database connections, expose internal stage boundaries, and measure normalization/query durations. This is domain/database timing, **not authenticated browser or HTTP latency**. The diagnostic files and result JSON remain ignored local artifacts.

## Measured findings

### 1. Candidate pagination still processes all accessible content first

Five consecutive 40-item `listContentPoolSelection` calls with the task's actual collection filter took **1,518 / 1,424 / 1,442 / 1,529 / 1,543 ms** (median 1,518 ms). Each call loads 95 projects and processes 5,796 accessible items to return 40 of 95 matching items.

An instrumented call took 1,531 ms:

- Light-row PostgreSQL query/transfer/driver decoding: 989 ms, 5,796 rows.
- `refreshProjectStats` normalization: 525 ms, 5,796 items.
- Collection/membership reads: two queries, 165 combined rows, 61 ms combined; these overlap the light-row read.
- The response is 149,857 UTF-8 bytes. JSON serialization rounded below 1 ms in the five-call sample.

`readContentPoolDeskRowsFromDb` receives only an optional owner restriction, not the selected collection/project/filter/cursor. Administrators have no owner restriction. `contentPoolSelectionContext` then normalizes every project **before** `scopeContentPoolProjectsByCollection`; `selectContentPoolItems` sorts matching results before `paginateContentPoolSelection` slices the page. Search, filter, pagination and forced refresh repeat this work.

The IDs-only selection used by "select all matching" took 1,448 ms: 935 ms for the same 5,796-row read and 503 ms normalization. It returns only 95 IDs, but that does not reduce its backend work.

Source boundaries: `src/lib/database.ts:1537`, `src/lib/content-pool.ts:582`, `src/lib/content-pool.ts:1191`, `src/lib/content-pool-selection.ts:116`.

### 2. Manual preview source preparation performs 95 expensive ID lookups

Calling `freezeContentPoolItemsByIds` with the actual 95 selected IDs took **4,881 ms**, returning 95 frozen values. This is one preview preparation stage; it is not the full schedule preview and is separate from configuration browsing.

- 95 ID-to-project containment queries execute with bounded concurrency.
- The distinct project read returns nine full project rows, taking 481 ms.
- Those projects contain 2,681 items; normalization takes 1,023 ms before selected snapshots are retained.

Do not add the individual concurrent query durations to claim wall time. The measured whole-call wall time is 4,881 ms. Sampling two random values happens after preparation; this stage freezes the entire manually selected candidate set under the current contract.

Source boundaries: `src/lib/database.ts:1463`, `src/lib/content-pool.ts:630`, `src/lib/canvas/scheduler.ts:1835`.

### 3. The ID lookup no longer reliably uses its existing GIN index

`EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` on selected IDs at positions 0, 47 and 94 showed **Seq Scan** each time: **301.450 / 277.291 / 275.127 ms**. These are executions against `content_projects`, not browser rendering or provider latency.

`idx_review_source_items` exists, is valid and ready, and is still 878 MB (`gin (data_json jsonb_path_ops)`). Therefore index absence is ruled out for this observation. An equivalent first-ID query in a separate `BEGIN READ ONLY` transaction with **transaction-local** `enable_seqscan=off` used Bitmap Index/Heap Scan and took **16.966 ms**, returning the same two project rows; the transaction was rolled back immediately. No persistent planner configuration was changed. This is an execution-plan comparison, not a proposed global tuning change or a complete fix.

The old November 3 single-ID GIN measurement (~0.35 ms) cannot be reused as evidence for today's execution path. The current planner chooses the sequential alternative; the exact reason for its cost decision requires separate planner/cost investigation. Automatic analyze had run earlier on November 16, so this investigation does not establish stale statistics as the cause. A point-in-time session check found no lock-waiting sessions; this does not rule out historical contention.

### 4. Cache size is not the observed problem for this query

The current page has an estimated cache size of 231,998 bytes under `JSON.stringify(page).length * 2`, below the existing 2 MiB limit. Therefore this query is cacheable. Cache remains in-memory with a 60-second TTL; a first open, expired entry, page reload or changed query still needs the slow backend path. Request deduplication and restoring a cached page do not accelerate those requests.

The previous isolated browser checks establish request counts and state restoration, not live runtime latency. The current investigation did not profile browser input/rendering, session-fetch latency or thumbnail networks; do not claim those are either the cause or ruled out.

## Repair direction

1. For configuration, stop reading/normalizing every accessible item per page. Keep owner visibility, project dropdown counts, collection descendants, deduplication, timestamp/media repair, sorting and cursor semantics explicit. Scope candidate reads before heavy normalization; separate compact navigation summaries from candidate payloads. A proposed implementation must be measured on this actual administrator/95-item collection case.
2. For preview, replace repeated whole-project JSON containment lookups with a predictable scoped lookup path, then read/normalize only required candidates. Preserve random seed, sampling, missing-ID errors, frozen snapshots and preview revision contracts. Do not change permanent PostgreSQL planner settings to conceal the query/storage problem. The item-table migration remains separately scoped P2 work.
3. Validate configuration opening, changing collection/search, load-more, select-all and preview separately. Measure authenticated browser/HTTP timing before claiming user-visible performance acceptance; request-count tests alone are insufficient.
