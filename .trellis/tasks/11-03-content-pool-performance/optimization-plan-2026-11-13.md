# 内容池编辑、画布状态恢复与批量调度筛选优化方案

日期：2026-11-13。状态：已授权执行并落地首批优化；实际范围、验证与剩余项见 `verification-2026-11-13.md`。本文保留完整阶段规划，不表示全部建议已实现。

本轮请求是制定优化措施。复用现有性能任务记录分析，不改变现有任务的实现范围，不启动数据库迁移。后续按阶段拆分实施；存储阶段需要独立任务，因为原 PRD 明确排除了 P2。

## 1. 结论和证据

| 问题 | 当前代码证据 | 影响 |
| --- | --- | --- |
| 保存完成后仍等待刷新 | `src/app/content/page.tsx` 的 `saveSourceEdits` 已用 PATCH 返回值更新编辑器和列表，但接着 `await refreshContentDesk()`；后者同时请求 desk 和 summary，直到二者结束才释放编辑锁 | 用户等待包括保存和后续读取；刷新还会重置列表，影响已加载位置 |
| 改一条仍重写项目 | `src/lib/content-pool.ts` 的 `updateSourceItem` 调用 `src/lib/database.ts` 的 `mutateContentProjectsForItemIdsInDb`；它锁定相关项目并写回整份 `data_json` | 已不再重写全表，但大项目 JSON、索引维护与同项目锁竞争仍是保存成本 |
| 列表分页尚未成为数据库分页 | `getContentPoolDesk` 读取可见范围的轻量条目，在 Node 中过滤、排序和分页；summary 单独装载同类上下文 | 只返回 40 条并不代表只读取 40 条，列表和统计存在重复扫描 |
| 画布选择器仍走全量读取 | `contentPoolSelectionContext` 调用 `readPool`，全量读项目并规范化，然后按权限/内容库过滤；`listContentPoolSelection` 最后才分页 | 每次打开、筛选和翻页都可能重复处理包括 raw 的大对象 |
| 刷新一个快照也全量查找 | `src/app/api/content-pool/selection/route.ts` 的 itemId 分支调用 `resolveContentPoolSelection({}, account)` 再 find | 单条刷新承担全池成本；已有按 ID 查询能力可复用 |
| 画布浏览状态随组件销毁 | `NodeInspector` 使用工作流 ID 和节点 ID 作为 key，关闭属性时卸载；`ContentPoolSnapshotPicker` 的 filter 和 `ContentPoolSelectionBrowser` 的 page 是组件内状态，重新挂载会发请求 | 内容库、项目、搜索、排序、已加载页和滚动位置无法恢复 |
| 已选素材已有持久化设计 | `contentPoolSnapshotConfig` 写入 sourceItemId、标题、正文、图片、视频和 snapshotAt；画布已有 900 ms 自动保存 | 不能断言已选素材根本没保存。确认丢失的是浏览状态；若成功保存后快照仍丢失，应单独检查保存/恢复链路 |
| 批量调度共用慢选择器 | `ContentPoolScheduleSourceEditor` 同样渲染 `ContentPoolSelectionBrowser`，调用相同 selection 接口 | 参数配置、搜索、库/标签筛选同样承担全池读取成本；多个参数还可能重复请求相同候选集 |
| 勾选也触发候选列表刷新 | 调度的 setItemIds 创建新的 source.filter，其中包含 itemIds/mode；选择器 load/effect 依赖整个 filter 对象，但请求 URL 不包含 itemIds/mode | 勾选/取消选择、切换选择模式会触发与原 URL 相同的列表请求，并可能重置已加载页 |
| 条件匹配预演读取并冻结全候选集 | `src/lib/canvas/scheduler.ts` 的 `resolveScheduleContentPool` 在 match 模式调用全量 resolve，再逐项冻结；fixed 模式最后才 slice(0, 1) | 仅使用一条也可能处理全部候选。manual 模式已有按 ID 冻结，需保留其定向读取能力 |
| 输入卡顿有待测量 | 编辑草稿状态在整个内容页；每次渲染计算 JSON dirty 对比，列表卡片内联遍历 | 有重渲染风险，但尚无本次 React 性能记录，不能直接认定是主要耗时 |

历史量级来自本任务 11 月 3 日 design/implement：约 5,100 条内容、项目 JSON 约 222 MB、raw 约 187 MB、GIN 约 878 MB；轻量扫描仍约 46 MB，desk 960 ms、summary 898 ms。这些不是今天的实测值，也不是本轮已取得的优化成果。

本轮只读确认 `http://127.0.0.1:3001/api/version` 返回 candidate、versioned=true，commit 为 `1cf2192effca0d4217e0970aca7eb2653bbf51d7`，与分析起点 HEAD 一致。

## 2. 优先级与实施措施

### P0-A：恢复画布节点状态，优先消除重复操作

1. 打开已有选择的节点时，先显示已保存快照卡片（标题、正文摘要、缩略图、选择状态），提供“更换素材”和“刷新当前快照”。打开属性不依赖候选列表加载；已有快照可立即使用。
2. 将项目、内容库、包含子集、搜索、标签、排序等偏好放入按账号/工作流/节点隔离的浏览状态。可用浏览器会话存储恢复页面刷新，组件外内存保存候选页及滚动位置。全量内容和媒体字节不写入 localStorage，不把候选列表塞进工作流图。
3. 浏览结果按账号及权限范围、规范化筛选和游标建立有容量上限的缓存，合并相同在途请求。建议以 60 秒有效期、最多 10 页作为初始预算，实际内存占用再测量调整；退出/切换账号时清空。不同节点保留各自筛选，不共享节点 UI 状态。
4. 有效缓存直接恢复；过期时保留列表并在打开时校验一次。删除、编辑、移动内容库等成功操作使相关缓存失效。跨标签页可用变更通知失效；其他用户的修改由下次打开时的有效期/版本校验发现，不增加定时轮询。
5. 请求加入 AbortController，筛选变化时立即废弃旧请求的结果，卸载时取消；保留已有搜索防抖。当前已有 loadSequence，但仅在下一次 load 开始时递增，需要覆盖防抖等待期间的旧响应。
6. 已选 sourceItemId 与快照继续使用现有工作流保存机制；确认自动保存成功、切换工作流、刷新页面和失败重试均不丢失选择。缓存更新不得自动覆盖冻结快照。原条目删除/权限失效时明确显示来源状态，并按既有快照访问契约处理。

主要范围：`src/app/canvas/page.tsx`、`src/components/canvas-schedule/shared.tsx`，必要的浏览状态辅助模块及隔离浏览器检查。共享选择器也服务调度参数，必须覆盖 single/manual/match 模式。

### P0-B：缩短编辑保存等待，保持正在编辑的位置

1. PATCH 成功即用服务端返回的规范化条目确认保存，解除保存锁。统计刷新不属于保存成功的前置条件；刷新失败显示独立提示，不能把已成功保存报告为失败。
2. 标题、正文、图片等修改优先局部更新当前卡片和编辑器，保留已加载页、当前条目和滚动位置。只有修改命中搜索/筛选/排序依赖时才重新验证相应列表；状态、标签等改变才刷新相应统计。
3. 后台刷新携带请求版本，禁止旧响应覆盖刚保存的内容或新输入的草稿。条目不再匹配当前筛选时，明确提示并处理离开时机，避免直接切到第一条。继续保留图片上传锁和未保存离开保护。
4. 输入阶段先用浏览器性能记录确认主线程开销，再将编辑草稿隔离到编辑组件，稳定列表卡片 props，并缓存基准表单/集合索引。现有列表已经分页；仅在多页加载导致明显长任务时增加虚拟列表。
5. 不引入每次按键发请求的自动保存。用户点击保存仍执行一次明确 PATCH；失败保留草稿并支持重试。

主要范围：`src/app/content/page.tsx`、`src/app/content/content-source-editor.tsx` 及现有编辑器检查。

### P0-C：批量任务调度参数配置与筛选

用户补充：批量任务调度中“内容池”参数的配置、筛选同样非常慢。纳入本方案的直接验收范围，与画布节点使用同一套查询优化。

1. 分离“候选查询条件”和“已选 ID/选择模式”。请求依赖规范化后的查询 key，不依赖整个 filter 对象；只改变 itemIds、manual/match 或参数名称时不重新查询候选，不清空已加载页。保留配置本身的保存，不把“不重新查询”误做成“不保存选择”。
2. 多个参数的相同查询共享有界数据缓存及在途请求，但每个参数各自保存筛选、勾选和滚动位置，状态键包含账号、调度/草稿 ID 和参数 ID。调度筛选已经存在 source.filter 中，应复用现有草稿/定义恢复；需补的是候选页缓存和返回位置，不能误判为完全未持久化。
3. 查询输入即时回显，沿用已有 240 ms 搜索防抖；多项高级筛选可采用暂存后“应用筛选”，一次提交条件。加载期间保留旧列表并显示更新状态，旧结果不能作为新条件下的“全选匹配”依据；快速切换时取消过期请求。
4. 未展开的参数候选浏览器按需加载；参数摘要仍显示已有选择/条件，避免打开调度配置就同时查询所有内容池参数。
5. “选择全部匹配”改为轻量 ID 查询并保持 200 条上限；不为获取 ID 连续加载每页完整正文/图片。成功选择后不再次刷新相同候选列表。

主要范围：`src/components/canvas-schedule/shared.tsx` 及批量创建/编辑中共享该组件的调用点。需覆盖任务组参数、结果项参数、固定单条、逐项和随机抽取。

### P1：减轻查询与重复扫描

1. `selection?itemId=...` 改为权限约束的按 ID 查询，只读取相关项目/条目并转换成现有返回结构。复用现有 item-scoped helper；保留跨项目 newest-project-wins、跨账号隔离和媒体规范化。
2. 候选列表改用无 raw 的轻量读取路径，尽早限制账号范围，按可行的项目条件收窄。候选卡片只返回标题、摘要、封面、媒体数量等展示字段，选中时再读取完整快照；点击选中后的等待、失败和取消必须明确。
3. 项目/库/标签导航与候选页解耦，翻页不重复携带全部导航统计。desk 和 summary 优先共享同一次读取的上下文或按需返回 summary，避免单次页面打开重复扫描。
4. 不将完整项目 JSON 放进长期内存缓存。列表缓存有范围、失效条件和大小上限；核心收益应来自读取数据量下降。
5. 保持 AND 标签语义、NFKC 搜索、缺失时间排序、子库范围、localMediaComplete、权限、媒体顺序以及旧游标契约；必要时对游标显式版本化。
6. 调度预演与候选浏览分开优化：manual 继续按选中 ID 冻结；match 先取得轻量候选 ID/排序字段/总数，校验数量上限后再读取实际需要冻结的内容。fixed 只读取排序后的首条完整内容；each 校验 200 条上限后批量加载；random 保持现有种子、抽样和不重复语义，禁止仅从浏览器当前 40 条里抽样。同次预演可以复用相同权限/筛选下的候选查询，但不跨预演复用过期快照，也不改变既有预演修订号和启动一致性契约。

主要范围：`src/app/api/content-pool/selection/route.ts`、desk 路由、`src/lib/content-pool.ts`、`src/lib/content-pool-selection.ts`、`src/lib/database.ts`、`src/lib/canvas/scheduler.ts` 和对应类型/消费者。

注意：轻量读取仍会扫描可见池，属于过渡优化，不能承诺稳定百毫秒查询。已有 PostgreSQL 证据显示直接在大型 JSON lateral 展开后添加过滤/窗口函数会触发重复解压，曾出现 63 秒查询，不能机械照搬数据库分页。

### P2：独立推进逐条存储，解决大数据量下的保存成本

1. 建立条目级存储，项目保留项目元数据；正文、媒体及人工编辑状态按条目保存，原始采集 raw 与高频编辑字段分离。库成员关系继续使用已有关系表。
2. 数据库直接完成权限过滤、条件筛选、排序和游标分页，按真实查询组合建立索引。搜索需单独验证当前中文/NFKC/标签匹配语义，不能用不等价的全文搜索替换。
3. 单条更新只写一条记录，使用版本检查防止并发覆盖。同步迁移采集导入、媒体回填、标签批处理、删除、Canvas/调度冻结及审查来源读取，不能保留两个长期独立可写的数据源。
4. 迁移前核对当前数据量和重复 ID，保留项目关联与跨账号身份，明确 newest-project-wins 的稳定映射；不能只用 sourceItemId 当全局主键。
5. 在隔离 SQLite/临时 PostgreSQL schema 验证，再制定维护窗口、备份、分批回填、数量/字段/媒体顺序校验和切换步骤。停止旧写入或采用可验证的增量同步后才能切换；切换后的新写入必须有回迁/恢复策略。
6. 旧 JSON 和 GIN 在所有读写消费者迁移、校验和回滚窗口结束前保留。删除旧索引不是本轮动作，也不能先删再测。

主要范围：数据库迁移、`src/lib/database.ts`、内容池领域服务及所有相关读写消费者。此阶段建立独立 PRD/design/implement，更新架构契约后再实施。

## 3. 验收与测量

以下均为拟定目标，非已实现的性能承诺。以同一台本地机器、同一数据规模和明确冷/热状态作前后对比；每条关键路径至少 30 次，记录 P50/P95、请求次数、响应字节和数据库读写量。认证测试分别覆盖成员与管理员。

| 场景 | 目标与判定 |
| --- | --- |
| 关闭再打开同一节点 | 已选快照及筛选恢复；有效缓存下列表恢复 P95 ≤ 100 ms，重复候选列表请求为 0 |
| A/B 节点切换、页面刷新 | 各节点浏览状态隔离；成功保存后 ID/快照不丢；账号切换无缓存泄漏 |
| 编辑输入 | 输入响应 P95 ≤ 100 ms；无每键网络请求；记录长正文和多图场景的主线程长任务 |
| 保存交互 | PATCH 成功到 UI 确认 ≤ 100 ms；不等待 summary，不丢草稿或滚动位置 |
| 保存总耗时 | P0/P1 在同规模下显著降低；P2 单条编辑 API P95 ≤ 300 ms，且无整项目 JSON 重写 |
| 候选页/列表 | P1 无 raw、无全池浏览器传输；P2 首屏 40 条 API P95 ≤ 300 ms，翻页 ≤ 200 ms；统计单独测量 |
| 单条快照刷新 | 不调用全池解析；已选条目删除、权限变化、媒体顺序均正确 |
| 调度参数勾选/取消 | 即时回显、滚动和已加载页保留；仅变更 itemIds/mode 不产生候选列表 GET |
| 调度筛选 | 相同有效查询缓存命中 ≤ 100 ms；搜索停顿后仅一次有效查询，高级筛选应用一次仅一次查询；P2 未缓存查询 API P95 ≤ 300 ms |
| 多参数配置 | 相同查询合并为一次请求；未展开参数不查询候选；参数之间、不同调度草稿之间状态隔离 |
| 调度预演 | 分别记录 manual/fixed/each/random 的耗时与读取量；只有最终选中项加载完整快照，数量上限、随机种子、冻结和启动修订号保持一致 |
| 正确性 | 搜索/排序/分页无重复遗漏，新增/编辑/删除后缓存更新，并发保存不静默覆盖；冻结运行输出保持不变 |

端到端耗时拆分为：输入渲染、PATCH 数据库读/锁/写、列表和统计请求、浏览器解析/渲染。缩略图与远端媒体加载单独统计，避免把媒体网络时间误判成数据库耗时。今天未进行认证用户性能复现，也未证实保存成功后的快照丢失。
